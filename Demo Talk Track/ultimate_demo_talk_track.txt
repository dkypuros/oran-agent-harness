O-RAN Agent Harness Lab - Ultimate Demo Talk Track
=========================================================================

Purpose
-------------------------------------------------------------------------
This is the live talk track for the simple two-loop O-RAN Agent Harness demo.

The key idea is simple:

The left loop is alert + harness.
The right loop is remediation + harness.

The assistant is helpful, but the assistant is not load-bearing. The harness is
load-bearing. The endpoints are stubbed, but the wiring, the routing decision,
the guardrail check, the sandbox verdict, and the AuditEvent contract are the
real thing.

That is the whole point of the demo.


Opening Frame
-------------------------------------------------------------------------
So, here's what I want to show you.

This is not a chatbot demo where the model just says something confident and
then we pretend that's operations. That's not what this is.

This is a harness demo.

And the reason I care about that distinction is because in a telco environment,
especially when you are talking about RAN, timing, O-Cloud, SMO, hardware,
firmware, drivers, Kubernetes, Redfish, Metal3, all of these things - the model
can't be the thing that is making the production decision.

The model can help the operator understand what happened.
The model can explain the evidence.
The model can help navigate the environment.

But the evidence has to come from somewhere else.

So what I'm showing here is a very small, very focused version of that idea.
There are two loops.

On the left side, we have the discovery loop. A PTP drift alert comes in. The
harness investigates it. It looks at the PTP signal, PHC behavior, Redfish,
Metal3, operator state, and the taxonomy. And then it says, "This looks like a
NIC / PHC hardware issue."

On the right side, we have the remediation loop. And this is the part that I
really want you to focus on. The right side is not just a static proposal. It is
also connected to a harness. It has a chat surface, it has slash commands, it has
stubbed O-RAN endpoints, and it has a harness-walker AuditEvent that becomes the
load-bearing proof.

So the left loop is alert + harness.
The right loop is remediation + harness.

That's the architecture.


Demo Flow Summary
-------------------------------------------------------------------------
The live flow is five moves:

1. Click /commands.
2. Click Pre-flight survey.
3. Switch the scenario to E: Firmware + SMO.
4. Click Run harness-walker sidecar.
5. Ask the assistant: "Explain what the harness walker just proved, and what
   remains blocked behind the operator?"

That flow is strong because it shows:

discover first -> choose remediation slice -> run harness evidence -> ask the
assistant to explain -> keep the harness load-bearing and keep production behind
operator control.

Now I'm going to click `Pre-flight survey`.

This is the "look before you touch" step.

Before I ask the system to do any remediation analysis, I want to know what the

- What is the bare-metal state?
- Is there a Redfish task already running?

We're not jumping from "I saw an alarm" straight to "apply a fix."

3. Switch scenario to E: Firmware + SMO
-------------------------------------------------------------------------
[Presenter action]
Switch the remediation slice from D: Driver / KMM to E: Firmware + SMO.

[Talk track]
Now I'm going to switch the scenario to `E: Firmware + SMO`.

This is where the demo gets more interesting.

The D path is useful because it shows a down-only remediation. The finding
becomes `host_driver`, router.py and taxonomy.yaml classify it, and the right

That's a clean story:

PTP / PHC issue -> host driver -> O2 IMS -> KMM.

But the E path gives us the dual-route story.

This is the part I really like because it shows both directions.

On the down route, the firmware remediation goes through O2 IMS into the
infrastructure side - Metal3, Redfish, the hardware lifecycle surfaces.

On the up route, the harness emits the service-side companion context through
SMO / TMF921.

So now we have:

node_firmware -> O2 IMS + TMF921.

That is the standards story.

The down route says, "This is infrastructure. This touches the O-Cloud and the
hardware lifecycle layer."

The up route says, "This also has service context. The SMO should know what is
happening. The intent envelope needs to be visible."

And that's exactly the nuance we wanted in this demo. We are not trying to model
every possible O-RAN remediation. We are showing one credible slice of how these
pieces connect.

The stubs are there so we can tell the story safely.
The harness is there so the story is real.

-------------------------------------------------------------------------
[Presenter action]
Click Run harness-walker sidecar.

[Talk track]
Now I'm going to click `Run harness-walker sidecar`.

This is the key moment.

Up until this point, the UI has been setting the scene. We looked at commands,

Now the harness-walker actually runs.

And when it runs, the topology becomes live.

You can see the orchestrator light up.
You can see router.py and taxonomy.yaml light up.
You can see guardrail.py and guardrails.yaml light up.
You can see the O2 IMS / O-Cloud Manager route.
You can see the Metal3 / Redfish or KMM endpoint depending on the scenario.
And for the E path, you can see the SMO / TMF921 up route as part of the story.

This is the part I would slow down on when presenting.

Because this is where we prove the demo is not just a visual.

The right loop asks harness-walker for an AuditEvent. That AuditEvent is what
records the remediation proposal, the routing decision, the guardrail result, the
sandbox verdict, the approval status, and the endpoint evidence.

So the assistant is not inventing this.
The UI is not inventing this.
The proof comes from the harness-walker result.

For the D path, the sidecar shows something like:

- action: `apply_kmm_module`
- target: `worker-ran-02.dallas.example.com`
- approval: `requiresHumanApproval=true`
- guardrail: pass
- sandbox: `apply_allowed=true`
- O2 IMS down route: accepted
- SMO up route: quiet, because driver-only remediation does not need a companion
  TMF921 intent

For the E path, the point is that the firmware remediation has both the down
route and the up route.

The down route is O2 IMS into the O-Cloud / hardware lifecycle side.
The up route is SMO / TMF921 so the service-side context is visible.

That is the O-RAN harness story in a small form.

The endpoints are stubs, but the contract is not fake.

The contract is:

- classify the fault deterministically
- route it through the taxonomy
- evaluate guardrails
- run the sandbox
- emit an AuditEvent
- expose the right O-RAN surfaces
- keep production blocked behind the operator

That is what the harness-walker proves.

What Just Happened - The Full Story
-------------------------------------------------------------------------
So if I step back, here's what just happened end to end.

The left loop gave us the finding.

A PTP drift alarm showed up on a timing-sensitive worker. The harness correlated
that with PHC behavior, hardware timestamp evidence, driver information, and the
other O-RAN-adjacent surfaces. The output of that loop was not "go fix it." The
output was a recommendation: this looks like a NIC / PHC hardware issue.

Then the right loop took over.

going to prepare a standards-backed remediation proposal and run it through the

That proposal can take different shapes.

The D path is driver / KMM. That is a down-only path:

host_driver -> O2 IMS -> KMM.

The E path is firmware + SMO. That is the dual-route path:

node_firmware -> O2 IMS / Metal3 / Redfish down,
and SMO / TMF921 up.

Then the harness-walker ran.

It produced an AuditEvent.
It showed what the router decided.
It showed what the taxonomy matched.
It showed what the guardrails allowed.
It showed what the sandbox simulation found.
It showed what endpoint route was active.
It showed what still required human approval.

Then the assistant explained the result.

And the key point is: the assistant explanation came after the harness evidence,
not before it.

That's the difference between this and a normal agent demo.

A normal agent demo often says, "Trust the model."

This demo says, "Trust the harness, inspect the evidence, and let the model help
the operator understand what happened."

That's the whole thing.

If Someone Asks: "Why Does This Matter?"
-------------------------------------------------------------------------
Because telco remediation is not one thing.

Sometimes it is down into the infrastructure.
Sometimes it is up into the service management layer.
Sometimes it is both.

A driver/KMM issue may only need the O2 IMS / O-Cloud path.
A firmware remediation may also need Metal3, Redfish, and SMO / TMF921 context.
A rejected maintenance window should stop the action even if the technical path
looks valid.

That is why the harness matters.

It lets us encode those boundaries.
It lets us show the operator the exact path.
It lets us explain what was proven.
And it prevents the assistant from becoming the production authority.

That's the future-facing part of the demo.

It's not just AI in front of telco operations.
It's AI inside a governed, standards-aware, evidence-backed operating loop.
